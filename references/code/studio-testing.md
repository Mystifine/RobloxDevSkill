# Testing in Studio

How to test through Studio MCP: specs that drive live services, and Play tests with real input, so the client path is tested, not only the remotes. For clicks, keys, prompts, the camera, moving the character and touch, read [play-input.md](play-input.md). What to verify is in [coding.md](coding.md#verify). Before judging UI, an effect or a world sign by a `screen_capture`, or catching a moment shorter than a few seconds, read [captures.md](captures.md).

## Studio MCP calls
- **An empty studio list with Studio open:** Studio's MCP server is switched on per Roblox account (Assistant > Manage MCP Servers). For 30 minutes the list stayed empty with Studio and `StudioMCP.exe` running and Rojo connected: the signed-in account's `%LOCALAPPDATA%\Roblox\AssistantSettings\<userId>.json` lacked `"mcp-server": {"enabled": true}`, which other accounts on the machine had. Read that file, then ask the owner to turn it on.
- **A call's `require` is its own copy:** anything a Studio MCP `execute_luau` call requires has its own module cache, so it gets a fresh copy of a service with none of the running game's state (a deck service answered nil while the player's save had loaded). To test live services run them from a temporary Script and remove it afterwards (a save library's reset, run through `execute_luau`, found no live session and deleted the player's record under it), read state through the game's own test hook (a BindableFunction it exposes in Studio), or drive the game through its own entry points (its prompts, remotes and UI: [play-input.md](play-input.md)). `_G` is shared across calls, so a harness defined in one stays callable from the next. Measured again in a Play server: requiring the data service from `execute_luau` and calling its get returned nil twice ("profile not loaded yet") 22 s after join, while the game's own copy had the profile loaded; the game's ServerStorage `BindableFunction` hook (`"get"`, `"set"`, `"call"`) returned the real profile at once. Tables cross a bindable as copies, which is fine for reads and for passing data to pure functions.
- **In Edit that cache also outlives source edits:** require a fresh clone (parented beside the original, or clone the whole folder and require from the clone, so its `script.Parent` requires resolve: parentless, a module requiring its siblings failed "Requested module experienced an error while loading"; destroyed after) to load the current source (`local m = module:Clone(); m.Parent = module.Parent; local T = require(m); m:Destroy()`), and a build tool's own requires go stale the same way: clone the constants it requires and assert the ids it needs (two icons added later resolved to nil and were built without, with no error).
- **A Client call sees the game's instances, not its module state:** a Client `execute_luau` call (or `studio_mcp.py luau --datamodel Client`) runs in its own VM, and its own require is a separate copy of the client controllers too. A pop-up stream run that way required an uninitialised copy of the HUD controller and drew nothing; a call that required a reveal controller and called its play function failed "attempt to index nil with '<another controller>'", while reading PlayerGui and its gradients worked. Drive client features through the game itself:
  - a LocalScript the call parents to PlayerGui shares the game's cache: driven through workspace attributes, one opened windows and forced a layout, and the same pop-up command sent through it drew the pop-ups;
  - the game's own remote, fired to the player from the server through the project's Studio test hook, played the real reveal animation; a remote library that multiplexes every channel over one RemoteEvent has no event to find by name, so call the game's own network module (its `FireClient`) through the hook instead: that drove the real hatch animation for a capture;
  - real input ([play-input.md](play-input.md)).

  A respawn empties PlayerGui and takes that LocalScript with it (the next scenario timed out and read as failed checks): a driver that must outlive a death goes under `PlayerScripts`.
- **Test scripts fire and observe; they never subscribe to the game's remotes:** a networking library that keeps one callback per event lets a test script's `OnClientEvent` replace the game's for the rest of the Play session. A QA script listening that way left a match running on the server with no match screen; a Client test script watching an action-result event stopped every result reaching the game's UI. Fire requests only (with a request id) and read the outcome on the server, or read state (instances, attributes, tracks).
- **That copy is enough for a self-contained module:** a keyed timeline that holds no game state plays in it unchanged, so each outcome of a random event can be played on demand with its callback times logged, in seconds rather than minutes of waiting for the rare one (four of six real rounds came up the same way). The final check still starts it through the game's own entry point.
- **Never rename Rojo-synced instances to swap in fresh copies:** a map rebuild renamed 21 synced instances (12 constants modules, a formatter and the builder folder) to `__Name`, parented clones under the real names, built in a spawned thread while other tool calls polled it for about 40 s, then destroyed the clones and renamed the originals back. Afterwards neither copy existed in Studio (the constants folder had 14 children for 26 files) while the files on disk were intact, and every Edit spec then failed "Requested module experienced an error while loading". Instead, in one synchronous call: clone the builder folder and the constants it requires into a temporary ServerStorage folder, require from there (their relative requires resolve among the clones), rebuild in place, destroy the folder. That rebuilt 32 stations across four bases, the module tree 138 of 138 after. A clone of a module that requires `Packages` fails out of place with the same error: require the unchanged original for those. After any swap, compare every `.luau` path on disk with Studio's tree (a script doing so found 137 of 137 after the repair). To recover lost synced instances, move their files out of the project and back: Rojo removes and re-adds them, and live sync stays intact for later edits.
- Studio MCP calls run one at a time, so a long call blocks every other. Start long work from a temporary Script and poll an attribute it writes.
- **"Target is not reachable ... No OnInvoke handler responded"** on a heavy script means it ran unbroken too long, about 3 s, not that it failed: yield now and then (a `task.wait()` every 20,000 calls fixed one). **The call is still running after that reply, so never start a second long run on top of it:** an integration suite launched through `execute_luau` answered "Target is not reachable" twice (the second 24 s after the first), and a third launch 21 s later reported 16 passed, 1 failed, a world-travel check finding the character back in the first world. The console showed three completed runs (17/0, 17/0, 16/1): the "unreachable" runs had kept going on the Play server, and their own travel test moved the shared character mid-check. A lone rerun passed 17/0, and 8 isolated travel rounds sampled every frame stayed in the destination world. Run suites and probes in `task.spawn`, write the result to a `StringValue` in ServerStorage, read it in a later call, and refuse a launch while the value says "running". A pacing model that ran a few minutes lost its whole output to that reply; wrapped in `task.spawn`, writing its text to a ServerStorage `StringValue` that was polled and then removed, it completed every time. **After any temporary clone, probe for leftovers by name:** a clone of the constants, left by a script whose cleanup edit had silently failed (a shell heredoc turned an escaped `\n` into a real newline, so the replace never matched), stayed in ReplicatedStorage for hours.
- **A reply is cut at 100,000 characters with no error,** which broke a JSON dump and base64 reads. Send base64 in pieces of 60,000 bytes.
- **A thread a call starts outlives the call:** a `task.spawn` in a Client `execute_luau` call kept running, and printing, for over two minutes after the call returned. It makes a cheap watcher through a whole match (the phase, the mouse location, what fired); give it a stop flag and clear it before leaving Play.
- **Check that Studio holds the code under test:** with `rojo serve` running and its socket established, Edit still held the old scripts after Play stopped (a new module missing, a changed `Source` unchanged), and waiting did not help. Before a test, read one changed script's `Source` in Edit, or look for a new module; when it is stale, reconnect the plugin or push the mapped sources through `studio_mcp.py luau` (a generated script setting each `Source`, kept out of context). A plugin can also stop applying changes mid-session while `rojo serve` runs on. The sign of that silent disconnect: a unit run that still counted 109 specs after two were added (111 expected). Comparing each path's source length between disk and Studio found 15 files behind; writing each file's source into Studio from disk and comparing again (245 of 245 equal) restored the test bed, and the run counted 111. Before each spec run, compare the spec count or the source lengths with disk: a disconnect looks like stale behaviour, not an error.
- **Before calling a build ready to publish, compare a hash of every script in Edit with disk:** one Edit call hashed 224 scripts and matched them to disk in seconds, and listed leftovers that exist only in Studio. Requiring the catalogs in Edit to prove them failed instead, with "Requested module experienced an error while loading" for 10 modules that passed in Play and in cloned sandboxes: a require error in Edit after edits can be the stale cache (above), not broken code.

- **Edit cannot reach the DataStores the Play server can:** an Edit `GetAsync` failed "502: API Services rejected request ... Access forbidden" while the Play server read and wrote the same store. Read and remove test keys from the Play server, and confirm a removal with `GetAsync` (nil), not `ListKeysAsync`, which still listed a key seconds after its removal returned true.
- **Undo may not record a call's edits:** `ChangeHistoryService:TryBeginRecording` returned nil inside an Edit `execute_luau` (seen once), so deleting 21 instances was no single undo step. Keep what a call removes recoverable another way (an export, a backup copy).
- **A Play started through MCP (`start_stop_play`) has no native top bar:** `GuiService:GetGuiInset()` read (0, 0), `StarterGui:GetCore("TopbarEnabled")` errored as unregistered and a `TopbarSafeInsets` ScreenGui spanned the whole 1920 x 1080, so a topbar row scaled from its height drew 11.7 times too large. Judge the topbar, and whatever is placed from the inset, in a Play the user starts, or report it unverified; hide the topbar gui for other captures. Another MCP-started Play read the inset as (0, 58), with a top-bar button at `AbsolutePosition` y -46: read the inset in each session rather than assuming either.
- **Compare a wall-clock schedule with an outside clock:** Studio Play's `Workspace:GetServerTimeNow()` matched the PC clock within 0.002 s while the PC ran 13.1 s ahead of two websites' UTC (its time service stopped), so a correct :00 and :30 schedule looked 13 s early in Studio. Measure the PC's offset before judging a UTC schedule in Studio; live servers keep their own time.

## Specs in Studio
Drive live services from a temporary Script (a spec as its child ModuleScript) that writes its result to an attribute you poll, in Play (Edit's require cache goes stale: above). Never let a test write live or the owner's saves (use a scratch/QA profile and restore what it changed), and delete every temporary Script, ModuleScript and server you started, but only once the work it started has finished and cleaned up: threads, connections and delayed work started from a script die with it, including those a module made when that script first required it. A match started from a temporary Script stopped dead when the Script was destroyed; a harness LocalScript destroyed right after a cutscene's stop took the cutscene's per-frame cleanup and a package's shared Heartbeat with it, so grades stacked; a probe destroyed right after toggling a controller killed the `task.delay` fades of its toasts, which stayed on screen for minutes like a stale-UI bug, while the game's own button faded them normally. Clear hold attributes, then wait out the timers it triggered (about 4 s after a stop) before destroying it, and judge no lingering UI before then. A spec never subscribes to the game's remotes (above).

**Copy the tester's whole save before any spec or dev hook that resets or overwrites a player's data:** an integration suite that resets the first player's profile ran against the owner's Studio save (an evolved character, its level, EXP and a set of skills) with no copy taken, and the save came back fresh. `DataStore:ListVersionsAsync` on the profile key showed versions about an hour apart (the newest 21 s old, the one before 2,625 s), so everything written between them was gone and could not be restored. Read the profile through the game's hook (`get`), write it to a file (a Luau table constructor where keys look like numbers: below), run, then restore it from the file: DataStore versions are no backup for recent minutes. Write it back one top-level section at a time (`set`) and leave the profile's metadata out (`SessionId`, `Locked`): restoring it would write a stale session lock over the live one. Then diff the restored profile key by key against the file: after an integration suite that resets the first player's profile, all 10 sections compared identical, only the running play timer had changed, and the next Play loaded them. The project's docs should say which specs reset a profile.

**A test that needs a truly new player** (the new-player path runs only on a profile that has never played, and Studio's QA store persists between Play sessions): read the tester's profile through the game's dev hook, write it down as a Luau table constructor (string keys quoted, number keys bracketed: JSON would have turned numeric-looking keys, such as a pet collection's, into another type), reset, test across a rejoin, then set it back section by section and confirm it on the next joins (it held in two later sessions).

**When the user's Play session blocks Edit, run pure modules and unit specs in Lune:** with Studio in the user's Play, Edit-only runs were blocked. A 120-line Lune runner that loads the project's modules from disk with shims (`game:GetService`, `Random`, `RunService`, the datatypes, package stubs) ran a 40-player pacing model in about 75 s, agreed with the Studio run's medians, ran four balance variants in parallel, and ran 166 of 169 unit specs (the 3 failures were missing shims). Its traps:
- a Rokit shim refuses a tool missing from the project's manifest: call the Lune binary Rokit already installed (adding Lune to the manifest stays the owner's call: [game-economy.md](../design/game-economy.md#economy-and-pacing));
- `fs` calls cannot yield inside a metamethod: read the files up front;
- an all-absorbing mock loops forever when iterated: give it `__iter`.
What needs the engine (layout, physics, remotes, DataStores) still runs in Studio.

**Probes** read state the way the game keeps it, so check what a probe reads before trusting a nil or a still value:
- **A position from a part, not from an unanchored Model's pivot:** a client probe read `Model:GetPivot()` of models flown by setting their parts' CFrames; with no `PrimaryPart` the pivot stayed at the spawn point for the whole flight, so the probe reported models that never moved. Reading a core part's `Position` (or setting a `PrimaryPart`) showed the flight.
- **Keep a probe in step with the UI it reads:** a toast probe written for Frame toasts read nothing once the toasts became TextLabels.
- **Code that clones a model from a template folder** (companions, pets, followers, any look loaded by id) can be tested before any asset exists: stand-ins dropped into that folder from the server mid-Play (two parts: a body, and a nose on the -Z front, pivot at the base) exercised the whole path. The placeholders were replaced live, a walker's pivot sat on the floor (y 0.00), a floater hovered at feet level plus its lift (1.14), both faced the owner's way (nose 1.00 ahead), and both kept their slots after a 16-stud walk.

**Prove every effect the UI lists:** find the code that applies each one, then force it in a fight. Six armor passives showed on an item page while nothing in combat read them. After wiring, a temporary Script in the game's own VM set each to 100% in the shared config table, wrapped the effects service to count what the server sent, and stood the player in the monster's reach: 3 of 3 blows dodged, 3 of 3 reflected, regen started inside the natural regen's delay, one stand-up then a knock-out, 12 of 12 hits crit, and heals came only with lifesteal on. A plugin-VM require runs a separate copy of the modules and proves nothing.

**Test a new control through its own press, never only through the server path it ends in:** a new saved boolean setting was added to the server's preference options and to the save schema, but the client's settings controller kept its own allowlist of boolean keys and asserted on anything else, so every press threw "SettingsController:29: Invalid preference" before any request left the client. Testing had set the switch through a server hook, which bypassed the client path, so the fault survived a whole round (its first button sat in the top-bar inset, where synthetic clicks cannot land: [play-input.md](play-input.md)). A probe on the button's `Activated` counted the click (1) while the saved value stayed false, and the client console held the assert. Add a new setting to every allowlist on both sides; when a press does nothing, probe `Activated` and read the client console before blaming input. With the key added, a real press flipped it and auto-swings started (EXP 3,568 to 3,798 in 4 s).
