# Testing in Studio

How to test through Studio MCP: specs that drive live services, and Play tests with real input, so the client path is tested, not only the remotes. What to verify is in [coding.md](coding.md#verify).

## Studio MCP calls
- **An empty studio list with Studio open:** Studio's MCP server is switched on per Roblox account (Assistant > Manage MCP Servers). For 30 minutes the list stayed empty with Studio and `StudioMCP.exe` running and Rojo connected: the signed-in account's `%LOCALAPPDATA%\Roblox\AssistantSettings\<userId>.json` lacked `"mcp-server": {"enabled": true}`, which other accounts on the machine had. Read that file, then ask the owner to turn it on.
- Anything a Studio MCP `execute_luau` call requires has its own module cache, so it gets a fresh copy of a service with none of the running game's state (a deck service answered nil while the player's save had loaded). To test live services run them from a temporary Script and remove it afterwards, read state through the game's own test hook (a BindableFunction it exposes in Studio), or drive the game through its own entry points (its prompts, remotes and UI: Play tests with real input, below). In Edit that cache also outlives source edits: require a fresh clone (parented beside the original, destroyed after) to load the current source. On the client the same goes for a LocalScript it parents to PlayerGui, which shares the game's cache: driven through workspace attributes, one opened windows and forced a layout. A respawn empties PlayerGui and takes that LocalScript with it (the next scenario timed out and read as failed checks): a driver that must outlive a death goes under `PlayerScripts`. `_G` is shared across calls, so a harness defined in one stays callable from the next.
- **That copy is enough for a self-contained module:** a keyed timeline that holds no game state plays in it unchanged, so each outcome of a random event can be played on demand with its callback times logged, in seconds rather than minutes of waiting for the rare one (four of six real rounds came up the same way). The final check still starts it through the game's own entry point.
- Studio MCP calls run one at a time, so a long call blocks every other. Start long work from a temporary Script and poll an attribute it writes.
- **"Target is not reachable ... No OnInvoke handler responded"** on a heavy script means it ran unbroken too long, about 3 s, not that it failed: yield now and then (a `task.wait()` every 20,000 calls fixed one).
- **A reply is cut at 100,000 characters with no error,** which broke a JSON dump and base64 reads. Send base64 in pieces of 60,000 bytes.
- **A thread a call starts outlives the call:** a `task.spawn` in a Client `execute_luau` call kept running, and printing, for over two minutes after the call returned. It makes a cheap watcher through a whole match (the phase, the mouse location, what fired); give it a stop flag and clear it before leaving Play.
- **Check that Studio holds the code under test:** with `rojo serve` running and its socket established, Edit still held the old scripts after Play stopped (a new module missing, a changed `Source` unchanged), and waiting did not help. Before a test, read one changed script's `Source` in Edit, or look for a new module; when it is stale, reconnect the plugin or push the mapped sources through `studio_mcp.py luau` (a generated script setting each `Source`, kept out of context). A plugin can also stop applying changes mid-session while `rojo serve` runs on.

- **Edit cannot reach the DataStores the Play server can:** an Edit `GetAsync` failed "502: API Services rejected request ... Access forbidden" while the Play server read and wrote the same store. Read and remove test keys from the Play server.
- **Undo may not record a call's edits:** `ChangeHistoryService:TryBeginRecording` returned nil inside an Edit `execute_luau` (seen once), so deleting 21 instances was no single undo step. Keep what a call removes recoverable another way (an export, a backup copy).
- **`screen_capture` with a camera position** timed out every other call in Edit, and the next capture returned the previous request's view: capture again with the same camera.

## Specs in Studio
Drive live services from a temporary Script (a spec as its child ModuleScript) that writes its result to an attribute you poll, in Play (Edit's require cache goes stale: above). Never let a test write live or the owner's saves (use a scratch/QA profile and restore what it changed), and delete every temporary Script, ModuleScript and server you started, but only once the work it started has finished and cleaned up: threads, connections and delayed work started from a script die with it, including those a module made when that script first required it. A match started from a temporary Script stopped dead when the Script was destroyed; a harness LocalScript destroyed right after a cutscene's stop took the cutscene's per-frame cleanup and a package's shared Heartbeat with it, so grades stacked. Clear hold attributes, then wait (about 4 s after a stop) before destroying it. Test scripts observe state (instances, attributes, tracks) and never connect to the game's remotes: a networking library that keeps one handler per channel lets a QA script's `OnClientEvent` replace the game's (a match then ran on the server with no match screen).

## Play tests with real input
- **Someone else may be in the session:** in a user's open Studio, input arrived that no tool call had sent, the mouse moved between calls, and Play stopped with no call. Log the mouse location with each input you send, treat input you did not send as the user's, and stop starting Play over them; clear any scratch-store setting at once, since their next Play would use it. A real pointer overrides the mouse tool's position, so a hover in a capture may not be yours.
- **Prompts:** a real key press (keyboard input: key down, about 150 ms, key up). `ProximityPrompt:InputHoldBegin()` then `InputHoldEnd()` from the Client DataModel has started a real match, but can also do nothing: confirm the effect. With the default `Exclusivity` (`OnePerButton`) only one prompt per key shows, so stand where only the target is in range and check which one is shown before pressing. Captures leave CoreGui out in Play too, so a prompt, the chat window and an `AvatarEditorService` dialog never show in one: confirm them by `ProximityPromptService.PromptShown` and `TextChannel.MessageReceived`.
- **Clicks** take GUI coordinates (`AbsolutePosition`, below the top-bar inset), for BillboardGuis too. A world SurfaceGui button, or any 3D object: its world point through `Camera:WorldToViewportPoint`, minus `GuiService:GetGuiInset()`; confirm with `ViewportPointToRay` that the ray hits the board. Take every target from the instances, never from a capture, which comes back scaled down (1296 x 729 for a 1920 x 1080 viewport: clicks placed from it landed about 1.48 times too far up and left). A click by `instance_path` on a control clipped out of its scrolling frame reports Success and does nothing: confirm that the result changed.
- **The device emulator scales clicks:** with a phone emulated, `user_mouse_input` by `instance_path` and by GUI coordinates both landed about 10% short (a button at GUI 591,176 got the pointer at 529,156). Measure the scale with one click and `GetMouseLocation` (it updates after a press, not after a move) before clicking small targets.
- **Camera:** after an `execute_luau` call the Studio assistant puts back a camera type that changed during it, either way, and logs "The execute_luau changed camera type. Resetting from ... back to ...": one a call made Scriptable returns to Custom, and one the game itself set to Custom during a call went back to Scriptable. Sample camera checks inside the call that triggers the change, and place the character for the game's own camera to face the target.
- **Moving the character:** raycast for the floor before teleporting it (a fall may trigger the game's rescue and send it to spawn), or walk with `Humanoid:MoveTo` (into a TrussPart to climb). Jump with `Humanoid:ChangeState(Enum.HumanoidStateType.Jumping)`: setting `Humanoid.Jump` or calling `Humanoid:Move` from an injected script does nothing, since the PlayerModule's ControlModule rewrites both every frame.
- **Timing:** input and capture calls take seconds, so input sent after a fixed wait lands late (keys arrived during a pose show and the turn auto-picked). Poll `execute_luau` until the phase is on screen, then send the input in the next call.
- **A window shorter than a round trip:** calls sent together still run one after another, so a mouse sweep sent beside the call that started a match arrived 11 s later and missed an 8 s window. Let the input start the action instead: a spawned client thread (above) waits until the mouse reaches a known spot, then starts it, so one mouse command moves there, waits, and sweeps on time.
- **Gamepad:** the keyboard tool's gamepad key codes (`DPadRight`, `ButtonA`) reach `InputBegan` with those `KeyCode`s and drive the bindings, but `GetLastInputType()` does not report a gamepad, so gamepad-only prompts and wording never show. Check those on a real gamepad.
- **Touch cannot be sent by a script:** in Play, `VirtualInputManager:SendTouchEvent` from a Client `execute_luau` fails with "lacking capability RobloxScript", `StudioDeviceEmulatorService` is not reachable, and `UserInputService.TouchEnabled` stays false.
- **Touch fallback, the gesture logic only:** keep the gesture handlers as named functions, temporarily patch the synced ModuleScript's `Source` so a workspace `BindableEvent` calls them, and build each touch's input table on the game's side: a `BindableEvent` copies tables, so a table sent through it fails the handler's identity checks on the same touch. Every gesture can then be driven in a real match; restore the source after (a Rojo sync does). It is not a touchscreen test: say so, and check a real device before calling touch done.
