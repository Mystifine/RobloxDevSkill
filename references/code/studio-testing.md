# Testing in Studio

How to test through Studio MCP: specs that drive live services, and Play tests with real input, so the client path is tested, not only the remotes. What to verify is in [coding.md](coding.md#verify).

## Studio MCP calls
- Anything a Studio MCP `execute_luau` call requires has its own module cache, so it gets a fresh copy of a service with none of the running game's state (a deck service answered nil while the player's save had loaded). To test live services run them from a temporary Script and remove it afterwards, or drive the game through its own entry points (its prompts, remotes and UI: Play tests with real input, below). In Edit that cache also outlives source edits: require a fresh clone (parented beside the original, destroyed after) to load the current source.
- **That copy is enough for a self-contained module:** a keyed timeline that holds no game state plays in it unchanged, so each outcome of a random event can be played on demand with its callback times logged, in seconds rather than minutes of waiting for the rare one (four of six real rounds came up the same way). The final check still starts it through the game's own entry point.
- Studio MCP calls run one at a time, so a long call blocks every other. Start long work from a temporary Script and poll an attribute it writes.
- **A thread a call starts outlives the call:** a `task.spawn` in a Client `execute_luau` call kept running, and printing, for over two minutes after the call returned. It makes a cheap watcher through a whole match (the phase, the mouse location, what fired); give it a stop flag and clear it before leaving Play.

## Specs in Studio
Drive live services from a temporary Script (a spec as its child ModuleScript) that writes its result to an attribute you poll, in Play (Edit's require cache goes stale: above). Never let a test write live or the owner's saves (use a scratch/QA profile and restore what it changed), and delete every temporary Script, ModuleScript and server you started. Test scripts observe state (instances, attributes, tracks) and never connect to the game's remotes: a networking library that keeps one handler per channel lets a QA script's `OnClientEvent` replace the game's (a match then ran on the server with no match screen).

## Play tests with real input
- **Someone else may be in the session:** in a user's open Studio, input arrived that no tool call had sent, the mouse moved between calls, and Play stopped with no call. Log the mouse location with each input you send, treat input you did not send as the user's, and stop starting Play over them; clear any scratch-store setting at once, since their next Play would use it. A real pointer overrides the mouse tool's position, so a hover in a capture may not be yours.
- **Prompts:** a real key press (keyboard input: key down, about 150 ms, key up). `ProximityPrompt:InputHoldBegin()` then `InputHoldEnd()` from the Client DataModel has started a real match, but can also do nothing: confirm the effect. With the default `Exclusivity` (`OnePerButton`) only one prompt per key shows, so stand where only the target is in range and check which one is shown before pressing.
- **Clicks** take GUI coordinates (`AbsolutePosition`, below the top-bar inset), for BillboardGuis too. A world SurfaceGui button: its world point through `Camera:WorldToViewportPoint`, minus `GuiService:GetGuiInset()`; confirm with `ViewportPointToRay` that the ray hits the board.
- **Camera:** a camera an `execute_luau` call made Scriptable is reset to Custom after the call, so place the character for the game's own camera to face the target.
- **Moving the character:** raycast for the floor before teleporting it (a fall may trigger the game's rescue and send it to spawn), or walk with `Humanoid:MoveTo` (into a TrussPart to climb). Jump with `Humanoid:ChangeState(Enum.HumanoidStateType.Jumping)`: setting `Humanoid.Jump` or calling `Humanoid:Move` from an injected script does nothing, since the PlayerModule's ControlModule rewrites both every frame.
- **Timing:** input and capture calls take seconds, so input sent after a fixed wait lands late (keys arrived during a pose show and the turn auto-picked). Poll `execute_luau` until the phase is on screen, then send the input in the next call.
- **A window shorter than a round trip:** calls sent together still run one after another, so a mouse sweep sent beside the call that started a match arrived 11 s later and missed an 8 s window. Let the input start the action instead: a spawned client thread (above) waits until the mouse reaches a known spot, then starts it, so one mouse command moves there, waits, and sweeps on time.
- **Gamepad:** the keyboard tool's gamepad key codes (`DPadRight`, `ButtonA`) reach `InputBegan` with those `KeyCode`s and drive the bindings, but `GetLastInputType()` does not report a gamepad, so gamepad-only prompts and wording never show. Check those on a real gamepad.
- **Touch cannot be sent by a script:** in Play, `VirtualInputManager:SendTouchEvent` from a Client `execute_luau` fails with "lacking capability RobloxScript", `StudioDeviceEmulatorService` is not reachable, and `UserInputService.TouchEnabled` stays false.
- **Touch fallback, the gesture logic only:** keep the gesture handlers as named functions, temporarily patch the synced ModuleScript's `Source` so a workspace `BindableEvent` calls them, and build each touch's input table on the game's side: a `BindableEvent` copies tables, so a table sent through it fails the handler's identity checks on the same touch. Every gesture can then be driven in a real match; restore the source after (a Rojo sync does). It is not a touchscreen test: say so, and check a real device before calling touch done.
