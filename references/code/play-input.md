# Play tests with real input

Driving a running game the way a player does through Studio MCP: prompts, clicks, the camera, moving the character, timing, gamepad and touch. Read from [studio-testing.md](studio-testing.md), whose call rules apply; what a capture shows and misses: [captures.md](captures.md).

- **Someone else may be in the session:** in a user's open Studio, input arrived that no tool call had sent, the mouse moved between calls, and Play stopped with no call. Log the mouse location with each input you send, treat input you did not send as the user's, and stop starting Play over them; clear any scratch-store setting at once, since their next Play would use it. A real pointer overrides the mouse tool's position, so a hover in a capture may not be yours.
- **Prompts:** a real key press (keyboard input: key down, about 150 ms, key up). `ProximityPrompt:InputHoldBegin()` then `InputHoldEnd()` from the Client DataModel has started a real match, but can also do nothing (on a `Custom`-style prompt it fired neither `PromptShown` nor `PromptTriggered`): confirm the effect. With the default `Exclusivity` (`OnePerButton`) only one prompt per key shows, so stand where only the target is in range and check which one is shown before pressing. Captures leave CoreGui out in Play too, so a prompt, the chat window and an `AvatarEditorService` dialog never show in one: confirm them by `ProximityPromptService.PromptShown` and `TextChannel.MessageReceived`. Every `AlwaysOnTop` BillboardGui is left out as well (in a part, under an attachment or in PlayerGui, a custom prompt included: one laid out at 224 x 94 px never appeared, at stud or pixel size): set `AlwaysOnTop` false while inspecting one, or check its layout numbers (`AbsoluteSize`, `WorldToViewportPoint`).
- **Clicks** take GUI coordinates (`AbsolutePosition`, below the top-bar inset: 58 px of `GuiService:GetGuiInset()`), for BillboardGuis too; in Play the call needs `datamodel_type` (`Client`) and the studio id. A world SurfaceGui button, or any 3D object: its world point through `Camera:WorldToViewportPoint`, minus `GuiService:GetGuiInset()`; confirm with `ViewportPointToRay` that the ray hits the board. Take every target from the instances, never from a capture, which comes back scaled down (1296 x 729 for a 1920 x 1080 viewport: clicks placed from it landed about 1.48 times too far up and left). Prefer `instance_path` where the tool takes one: a click at `AbsolutePosition` plus the GUI inset missed a button (GUI coordinates already sit below the inset), and the same click by `instance_path` pressed it. A capture the same size as the viewport is no better, since its pixels include the top bar that GUI coordinates start below: `moveTo` x/y and a click at a button's centre read from one did nothing, twice in one session; in another, a click at a menu button's capture centre (47, 345 on a 1549 x 755 capture) did nothing, its `AbsolutePosition` spanning y 250-322, 58 px higher. In both, `moveTo` with `instance_path` hit at once, buttons inside an open window too. **A click reports Success whether or not its target could be seen:** by `instance_path` on a control clipped out of its scrolling frame it did nothing; on a side-menu button the game slides off screen while a window is open, it returned "Success" twice, nothing opened and the open window stayed up. Close the covering window first (its header Close, by `instance_path`) or check the target is on screen (`Visible` up its tree, inside the viewport and its clipping frame), then confirm the result changed: after the close, the same click opened the shop. A click fires the button's `Activated`; when nothing opens, read the console before blaming the click (one was the view's build error).
- **A control in the top bar's strip cannot be clicked at all:** a button in a `TopbarSafeInsets` ScreenGui (`AbsolutePosition` y -46) left its window shut to `user_mouse_input` by `instance_path` and by screen coordinates (238, 34), while buttons below the inset clicked by `instance_path`. Open what it opens through a LocalScript driver in PlayerGui ([studio-testing.md](studio-testing.md#studio-mcp-calls)): one created from the Client datamodel ran in the game's VM, required the real UI controller and opened the window when a workspace attribute changed. Report the button's own press as untested.
- **The device emulator scales clicks:** with a phone emulated (viewport 749 x 381), `user_mouse_input` by `instance_path` and by GUI coordinates both landed about 10% short (a button at GUI 591,176 got the pointer at 529,156), and clicks at GUI position / 0.9 hit every time. Measure the scale with one click and `GetMouseLocation` (it updates after a press, not after a move) before clicking small targets.
- **Camera:** after an `execute_luau` call the Studio assistant puts back a camera type that changed during it, either way, and logs "The execute_luau changed camera type. Resetting from ... back to ...": one a call made Scriptable returns to Custom, and one the game itself set to Custom during a call went back to Scriptable. Sample camera checks inside the call that triggers the change, and place the character for the game's own camera to face the target. A probe that must hold the camera binds `RunService:BindToRenderStep` at `Enum.RenderPriority.Last.Value`: the game's camera script set `CameraType` back every frame until then. **A camera still scripted after a scene is not always the tool:** one left `Scriptable` at FOV 64 sixteen seconds after a cutscene was blamed on the MCP tool for a whole round, while the scene's own `WaitForChild("PlayerModule", 5)` was returning nil after 5 s, twice per scene, in a place with no PlayerModule ([cutscenes.md](../art/cutscenes.md)). Time the scene's own start and stop path (when it takes the camera, when it hands it back) before blaming the test tool.
- **Moving the character:** raycast for the floor before teleporting it (a fall may trigger the game's rescue and send it to spawn), or walk with `Humanoid:MoveTo` (into a TrussPart to climb). Jump with `Humanoid:ChangeState(Enum.HumanoidStateType.Jumping)`: setting `Humanoid.Jump` or calling `Humanoid:Move` from an injected script does nothing, since the PlayerModule's ControlModule rewrites both every frame. **A trigger the client checks** (a walk-on pad, a zone a client loop reads) **needs the character moved from the client:** characters put on a purchase pad by the server (`PivotTo` in the Server datamodel) stood on it by every position read, yet the client's walk-on check fired nothing in three tries; the same move made from the client fired at once (the toast refusing a step whose predecessor was not owned, then, with 100 of the currency, the purchase toast).
- **Timing:** input and capture calls take seconds, so input sent after a fixed wait lands late (keys arrived during a pose show and the turn auto-picked). Poll `execute_luau` until the phase is on screen, then send the input in the next call.
- **A window shorter than a round trip:** calls sent together still run one after another, so a mouse sweep sent beside the call that started a match arrived 11 s later and missed an 8 s window. Let the input start the action instead: a spawned client thread (one outlives its call: [studio-testing.md](studio-testing.md#studio-mcp-calls)) waits until the mouse reaches a known spot, then starts it, so one mouse command moves there, waits, and sweeps on time.
- **Gamepad:** the keyboard tool's (`user_keyboard_input`) gamepad key codes (`DPadRight`, `ButtonA`) reach `InputBegan` with those `KeyCode`s and drive the bindings, but `GetLastInputType()` does not report a gamepad, so gamepad-only prompts and wording never show. Check those on a real gamepad.
- **Touch cannot be sent by a script:** in Play, `VirtualInputManager:SendTouchEvent` from a Client `execute_luau` fails with "lacking capability RobloxScript", `StudioDeviceEmulatorService` is not reachable, and `UserInputService.TouchEnabled` stays false.
- **Touch fallback, the gesture logic only:** keep the gesture handlers as named functions, temporarily patch the synced ModuleScript's `Source` so a workspace `BindableEvent` calls them, and build each touch's input table on the game's side: a `BindableEvent` copies tables, so a table sent through it fails the handler's identity checks on the same touch. Every gesture can then be driven in a real match; restore the source after (a Rojo sync does). It is not a touchscreen test: say so, and check a real device before calling touch done.
