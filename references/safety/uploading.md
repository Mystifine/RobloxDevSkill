# Uploading (Open Cloud)

- **Gate every upload.** Moderation screens each new upload with its own rules whatever the experience's label, can misfire, and can strike the uploading account.
  - Reuse an existing asset when one does the job. Size an image for its use first ([icons.md](../ui/icons.md)).
  - Screen the file at full size and at 128 px against [no-gore.md](no-gore.md), and [characters.md](characters.md) for character art; name it plainly. Look before the upload command runs, in an earlier step, a repaint or recolor included.
  - Upload one asset of a new kind first and wait: poll `GET https://apis.roblox.com/assets/v1/operations/{operationId}` until `done`, and go on only when `response.moderationResult.moderationState` is `Approved`.
  - Never upload to test moderation or resend a rejected file unchanged. For a rejection that looks wrong, pause the batch and appeal it.
- **Use the project's Open Cloud API key** (its ignored `.env` or secret store) for every asset type and experience operation; without one, ask the user, never search other projects or their `.env` files. A key the user gives goes in one file in the session's scratch folder, reaches the upload only as `--env-file`, and is deleted after the uploads; then search the project for leaks and tell the user a key pasted into a chat should be rotated. Never print the key or copy it into source, manifests, logs or Studio. The content rules ([assets.md](assets.md)'s audit, [characters.md](characters.md), [no-gore.md](no-gore.md)) apply to every upload.
- **Upload with [scripts/upload_asset.py](../../scripts/upload_asset.py)** `FILE [FILE ...] --group ID` (or `--user ID`), a batch's files in one call: it waits for moderation, exits 0 only when approved, retries a refused (403) request once a minute later, and stops a batch at the first file that is not. With `--manifest assets.json` it keeps ids by file stem and reuses what is approved at the same hash, so a batch can be rerun after any change. An asset still `Reviewing` when its operation ends is polled until it settles; one that outlasts `--timeout` exits 3, stays in the manifest as under review, and a rerun asks again instead of resending. A loop of calls stops at the first non-zero exit and shows each call's output whole: one piping each upload through `tail -1 | cut`, which printed an empty line for a refusal, ran on over five files and sent twelve refused requests to a moderated account.
- **`User is moderated`** (403 `{"errors":[{"code":0,"message":"User is moderated"}]}`) is a hold on the account behind the key, not a failed upload: every call with that key fails, reads included, while Studio's own session works on, and `upload_asset.py` stops at once (exit 4). Stop every upload, tell the user, and never retry, resend, or switch key or account. Once the key works again, read each asset the batch sent (`GET assets/v1/assets/{id}?readMask=moderationResult` on `https://apis.roblox.com`, and `GET assets/v1/operations/{id}` for each operation's response) before naming a cause, and call the cause unknown unless one is Rejected: one hold followed an image rejected minutes after its Decal read Approved, and another lifted within half an hour with every asset Approved, though an agent had already blamed the image being polled when the hold came (the 20th of its batch) and written that guess into a handoff, a brief and a memory. Resume one file a call, checking each: 44 of 44 then went up Approved, a 20 s pause apiece.
- **A Decal upload's id is not its image's id.** `upload_asset.py` uploads images as Decals and returns the Decal's id, which an ImageLabel rejects ("Asset type does not match requested type", or `AssetFetchStatus.Failure`). Store the image id from the Decal's `Texture` (`InsertService:LoadAsset(decalId)` in Studio) in the asset table and the upload record.
- **Before calling a key dead, read the variable names in its file:** a project key answered 401 Invalid API Key; the owner pasted a new one, which the `.env` then held as `ROBLOX_CLOUD_API_KEY` while the reader looked for the old `ROBLOX_API_KEY` and found nothing. With the new name read, the key worked.
- **Without a working key** (one answered 401 Invalid API Key), **publish through Studio,** under the same gate: images with Studio MCP's `upload_image` from a file served on `http://127.0.0.1` (`python -m http.server`), which returns image ids that load at once with no Decal step, owned by the Studio user and loading in a group's place; animations with `AssetService:CreateAssetAsync(sequence, Enum.AssetType.Animation, { CreatorId = groupId, CreatorType = Enum.AssetCreatorType.Group })` from Edit through Studio MCP, which published 6 clips, then 111, to an experience's group, all of which played in Play, though the reference lists only Model, Plugin, Mesh, Image and Audio. Its creator defaults to the Studio user, so always name the owner. Meshes go the same way: a Blender model's vertex data, rebuilt in Edit as EditableMeshes and published with `AssetService:CreateAssetAsync(mesh, Enum.AssetType.Mesh, ...)` to the experience's group (the build, its numbers and placing the parts: [editable-mesh.md](../art/editable-mesh.md)). Models (an FBX) can go through Studio MCP's `open_cloud_invoke`, posting to `/assets/v1/assets` as a Model for a group with the Assistant's own token, but only from a folder the owner approved: it refused a file "not inside a directory approved for uploads", with an instruction not to copy or move files to get around it. Ask the owner once to approve the folder (Assistant Settings, MCP Permissions) or renew the key, and carry on with everything else meanwhile.
- **Check that an image loads with an `ImageLabel`, never with `ContentProvider:PreloadAsync`:** a picture uploaded through `upload_image` reported `AssetFetchStatus.Failure` from `ContentProvider:PreloadAsync({ "rbxassetid://..." })` for 20 minutes, which looked like a pending moderation, while Open Cloud read it as Approved and Active. A known-good icon from an earlier round failed the same probe, and an `ImageLabel` with either id reached `IsLoaded = true` within seconds: the probe was wrong, not the upload. Judge by `IsLoaded`, or by Open Cloud's moderation state.
- **Approved does not mean loadable:** the API can say Approved and `Texture` give an image id while the image draws blank and the console says "Asset has not been reviewed", for over 16 minutes once. Read the console before suspecting the id. A fresh mesh or SurfaceAppearance map can show white or fail ("HttpError: NetFail") in the first Play after its upload, and a SurfaceAppearance that failed does not retry in that session: check it again in a second Play session before calling it broken. Loaded before its review, an image can stay unloadable for the session: a Decal's image id put in an ImageLabel seconds after the upload reported Approved logged "Asset has not been reviewed", and afterwards `IsLoaded` stayed false for the rest of the Studio session under `rbxassetid`, in Edit and Play, while `ContentProvider:PreloadAsync` said Success, `AssetService:CreateEditableImageAsync` returned 768 x 396 pixels, and the assetdelivery URL and `rbxthumb` forms loaded. Poll the image id's own moderation state before the first load check; when `IsLoaded` sticks false after an early fetch, confirm by pixels or a URL form instead of uploading again.
- **Once a pipeline's uploads are recorded, delete its intermediates** *(default)*: asset folders held each image set's whole pipeline beside its masters (`originals/`, `raw/`, `upload/` and `upload_named/` copies, contact sheets, reports, measurement and verification JSON, `__pycache__` and one-off scripts), plus a superseded Blender animation set (85 MB) and a verification-capture folder (13 MB). Removing them took the folder from 192 MB to 60 MB and left the game unaffected, since every id lives in code. Keep the masters, the receipts (`assets.json`) and the prompt files.
- **The experience's owner must own what it loads.** Read it in Studio first (`game.CreatorType`, `game.CreatorId`) and set `creationContext.creator` to that group (`groupId`) or user. An animation plays only in experiences its creator owns; Studio publishing (`AssetService:CreateAssetAsync`) must target the same creator. Upload animations as a `.rbxm` saved from Studio; Roblox warns that files edited elsewhere may fail.
  - **Wrong owner, the signs:** a Model fails `InsertService:LoadAsset` in Studio ("User is not authorized to access Asset"), and a user's key cannot grant a group's experience use of it (`CannotManageSubject`).
  - **A group's experience with only a user's key: try in order**, before asking the user or making anything public:
    1. Upload to the group with that same key (`upload_asset.py FILE --group <CreatorId>`). It works when the key's user may manage the group's assets (approved and loading in the group's place, after the universe grant was refused).
    2. If the group upload is refused, ask for a key owned by the group or by an account that manages its assets.
    3. Last, make the asset public (next item).
- **An asset another creator owns** (a key from a different account) must be public before the experience can load it. Images, decals and meshes start Open Use unless that account turned on Asset Privacy; sounds, videos and models start restricted, so grant them to everyone with `PATCH https://apis.roblox.com/asset-permissions-api/v1/assets/permissions` (beta; key scope `asset-permissions:write`; `subjectType` `All` with an empty `subjectId`, the ids in `requests`, `action` per the reference schema) or on the asset's Creator Hub permissions. Check `successAssetIds`, confirm each id loads in the experience, and report any that stay private.
