# UI: live state, performance and world-space GUIs

## State

- **`ResetOnSpawn = false` on nearly every GUI container** (ScreenGui, and any BillboardGui or SurfaceGui parented under PlayerGui: HUD, menus, shop, tutorial, offers). Build once at join and keep it across respawns; with the default `true` the whole UI is destroyed and rebuilt on every death, losing open windows, scroll positions, tweens and connections. Only UI that truly belongs to one character (an overhead billboard) lives and dies with it.
- **State lives outside the instances.** Keep one source of truth per fact (a store, a Pulse/signal value or the replicated save), and have the UI render from it and write back through it: never read a TextLabel's text or a Frame's `Visible` to decide logic. Views subscribe, update only when the value changes, and are safe to show, hide and re-show. State means facts (data, the open window, a selection), not every property: a reactive value or effect per instance property costs far more than the write it wraps.
- **A reward's effect goes before its payout,** so a counter can hold the rise back until the collected coins land (hold, release, finish): paid first, the currency reached the counter before the effect and showed at once. Keep a client fallback that rewinds a rise from the last 0.6 s when the effect comes late.
- **A server restyle resets nothing the client tweened:** a client tween turned an overhead tag's gradient (`Rotation` 0 to 360) at the top stage; the server's next style set `Rotation` 0, equal to its own last replicated value, so nothing replicated and the client kept 72 degrees (sampled after the restyle on a stage meant to rest at 0). On every style change, the client puts back each property its tweens touch (each motion's resting angle and offset, from a constants function both sides share) before starting the new stage's tweens.
- **A join cover lifts on data readiness, and the client asks for nothing before then:** a "your data is still loading" toast at join came from a client request (opening an arena) sent before the profile loaded, refused with `SAVE_UNAVAILABLE` and toasted. Holding that request until the data was ready, silencing that one refusal before then, and lifting a self-contained `ReplicatedFirst` cover on a local data-ready attribute removed it: no refused request in the join log. The snapshot poll had waited 1 s between tries under a 0.5-per-second rate limit; woken by the server's first state update instead, it fetched the data at once.
- **Survive respawn, rejoin and teleport:** derive what is open or selected from the store, re-bind to the new character (`CharacterAdded`) instead of rebuilding the UI, and restore on join from the saved or replicated state. Disconnect every listener when a view closes or is destroyed, and keep temporary state (a hover, a draft) out of the save.

## Performance

- Build once, then show/hide; do not recreate frames on every open. Pool list rows and virtualize long lists.
- Update text/images only when the value changes. No per-frame property writes for static UI; drive animation with `TweenService` or one shared loop.
- Avoid stacked full-screen transparent frames, many `UIStroke`/`UIGradient` on large lists, and deep `ClipsDescendants` chains.
- **Round a size read back from `AbsoluteSize` with a tolerance, and write only on a real change:** a ScrollingFrame's canvas was set to `ceil(body.AbsoluteSize.Y * windowUnits / windowPx) + 10` units. The body was a whole 636 units tall, but the read came back a float32 step either side of 636 (`AbsoluteSize.Y` 615.68335 and 615.683289), since the body's `Size.Y.Scale` (0.984520137 and 0.982998431) is a share of the canvas. So the canvas went 646, 647, 646 every frame, each change resizing the body and firing its `AbsoluteSize` signal again: `CanvasSize.Y.Scale` alternated 1.15357149 and 1.15535712, with a layout flush under `deferredThreads` every frame. The only sign on screen was a slow client while a window stood open. `ceil(x - 0.05)` ended it: 0 changes in 2 s. When code sets a canvas or container from a measured `AbsoluteSize` in a scale-only layout, watch `CanvasSize` over 10 `Heartbeat`s with the window idle. Finding such a loop: [performance.md](../code/performance.md#how-to-measure).
- **Build a large subtree detached and parent it once; stream long lists after the open tween:** parenting each new instance straight into a visible, laid-out window costs the engine far more than placing the finished subtree once: a shop's first open fell from 560 to 210 ms of script with a pixel-identical result. Anything that reads `Absolute*` during the build must wait until the subtree is parented (look a scroller up at drag start, not at build). A 56-row list (about 3,700 instances) built two rows at once, then the rest on `Heartbeat` within 4 ms a frame once the 0.24 s open tween ended: the click cost 20 ms, with every row present and in order.
- **A layout or UI scheduler never re-defers itself from its own flush:** a scale-layout library queued work with `if scheduled then return end; scheduled = true; task.defer(flush)`, and `flush` reset `scheduled` first, then refreshed nodes whose size changes queued their parents and children again, so each wave of a deep window deferred the next. The engine logged "Exponential deferred event growth detected calling task.defer" (its stack: the defer line, then the flush) and dropped the chain; `scheduled` stayed true for good, so no layout ran again and windows sometimes never appeared. The fix: drain the dirty set in passes inside one flush (work queued during a pass waits for the next), cap the passes (48) and carry the rest to `RunService.Heartbeat:Once`, cap deferred flushes per frame (6, then Heartbeat), `pcall` each node so one error cannot wedge the flag, and reschedule a flag older than 1 s. Afterwards five windows opened and closed in a row with no warning.
- **What moves every frame stays out of the layout kit:** a tutorial ring round a HUD element, made with the project's scale-layout kit and sized each frame from the element's `AbsoluteSize`, drew as a small square at the element's left edge (the kit kept its layout size), while an arrow positioned the same way was right; a kit-made TextLabel inside a BillboardGui did not show at all. Built with `Instance.new`, both drew as intended. A kit's managed frames are for authored layout; anything sized or placed per frame, and BillboardGui contents, are plain instances.

## World-space GUIs (BillboardGui, SurfaceGui)

- **BillboardGui defaults: scaled size, world-space placement.** Size with Scale (`UDim2.fromScale`, so it is measured in studs and shrinks with distance like the world), with both `Size` offsets at zero. Position it with `StudsOffsetWorldSpace`, never `StudsOffset` *(default)*: `StudsOffset` lifts along the camera's axes, so the label slides as the camera turns, while `StudsOffsetWorldSpace` lifts along the adornee's own axes and stays put; it is distinct from a UI dimension's pixel offset. Those axes turn with the part: on a cylinder stood upright (turned 90° on Z) the lift pointed sideways and the label sat beside the prop, so adorn labels over props to an invisible, unrotated anchor part. Set `Adornee`, `MaxDistance` and `AlwaysOnTop` deliberately (always-on-top only for pointers that must show through walls), `LightInfluence = 0` for UI, and keep it small and cheap: one per target, not per frame. Captures leave `AlwaysOnTop` ones out ([play-input.md](../code/play-input.md)). Check both on every billboard you build before calling it done: an event portal's countdown billboard shipped with a background plate and stroke and without the world-space offset, and the user asked for `StudsOffsetWorldSpace` and for the plate and stroke to go, with the same bare text on the HUD's countdown. **Hovering labels** (event countdowns) are bare text when the owner wants them to hover.
- **A BillboardGui whose adornee streamed out draws mid-screen:** labels kept in PlayerGui for parts in other worlds lost their `Adornee` under StreamingEnabled and stacked in the centre of the screen. Follow the anchor by name inside its model (`ChildAdded`, `ChildRemoved`) and set `Enabled = false` while it has none.
- **Inside a stud-sized board, lay out in shares:** a design canvas in pixels (40 a stud, say) with every child sized and placed as a share of its parent, so the board scales as one; pixel sizes inside stay fixed while the board grows and shrinks. Choose the studs at the nearest and farthest usual viewing distances: a label 16 studs wide filled the screen from 15 studs and one 12 wide was too small from 40; 13 x 4.3 studs settled it.
- **World text where the camera passes close fades as the camera nears it:** a 20 x 4.6 stud SurfaceGui plate at head height on a gate wall filled the bottom half of the screen whenever the player stood just inside the gate, since the trailing third-person camera sat behind the wall next to it. Fading the plate by the camera's distance to its rectangle (whole from 18 studs, gone within 10, quantised to twentieths so a still camera writes nothing) removed it from that spot while it still reads on approach. Check text in gates, doorways and corridors from inside them.
- **A world plate and a HUD bar never show the same thing:** a 2x-scale boss kept a name plate over its head, and at melee range its head sat near the top of the screen, so the plate drew behind the HUD boss bar that already showed its name and health (seen in captures). Remove the plate while the bar shows.
- **A world label that must keep its screen size** (damage numbers) stays scale-only: set its Size each frame from the camera distance, `2 * d * tan(fov / 2) / viewportY` studs a pixel times the pixels wanted (a share of the screen per device class).
- **Floating numbers in a burst:** each new one pushes the live ones up (eased over about 0.1 s, a crit's tag counted) rather than relying on timing: alternating sides with a faster float still overlapped 18% and a growing crit covered the number above it; nudged, 0% across seven bursts at a 0.3 s hit pace. Measure overlap by projecting each label's `TextBounds` times its `UIScale` on screen every 50 ms.
- **SurfaceGui:** fix its `Face`, set `SizingMode` and `PixelsPerStud` deliberately (a legible density at the distance it is read), `LightInfluence` and `AlwaysOnTop` on purpose, and keep text large enough to read at that distance.
- **3D UI in front of the camera** (held items, panels near the player): parts parented to the camera, each face a `FixedSize` SurfaceGui, moved with `workspace:BulkMoveTo` in a render step bound after the camera's (`Enum.RenderPriority.Camera.Value + 1`). A flat UI component works on them unchanged except its text limits: `MaxTextSize` counts canvas pixels, so it needs larger values. Hit-test with a ray against each part's plane; no physics query is needed.
- **A pointer at (-1, -1) is no pointer:** `UserInputService:GetMouseLocation()` reads -1, -1 in Play while the mouse is outside the game view. A pointer-driven camera took it as the top-left corner and leaned fully that way; treat it as no input and ease back to rest.
- **Overhead health bars take a solid dark outline** *(default)*: a pill with a white rim at 0.35 transparency over a dark fill read grey, and the owner asked for black; the rim became solid black, 2 px. Never a translucent light rim.
- **A world sign that states a requirement or a price is opaque, its key number on a solid pill** *(default)*: a SurfaceGui sign with `BackgroundTransparency` 0.32 and a rim at 0.45, on a see-through gate wall, its number in 48 px coloured text, read as faded. An opaque panel, a solid rim, 64 px text and the 72 px value in white on a solid green or red pill read clearly from about 40 studs in Play.
- **A SurfaceGui in front of translucent geometry sits on an opaque backer, never an invisible plate:** gate signs on a fully transparent plate 0.17 studs in front of a gate's 50%-transparent wall looked faded and tinted after the first gate, as if something were layered on top; the first gate's wall is 84% transparent, so its sign looked right, the sign that it was a blend and not the text. A transparent part writes no depth, so the translucent wall behind is blended over the GUI. An opaque backer in the panel's rounded shape (two crossed boxes and four corner cylinders, layers 0.03 studs apart so no faces meet, 0.06 clear of the wall) made the sign crisp in Play with the wall up; 80 gates audited 0 z-fight pairs.
- **An interactive SurfaceGui's part keeps `CanQuery` true:** a builder set `CanQuery` false on every anchor; the boards drew normally, but no mouse click reached their page buttons. With `CanQuery` true on the screen part, all four boards paged with real clicks.
- The same rules still apply inside them: bounds and rounded corners, readable text, the project's theme, build once and show or hide, state outside the instances.
