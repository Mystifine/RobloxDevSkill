# UI

Everything here applies to **ScreenGui, BillboardGui and SurfaceGui** alike. Add only what the task needs: [topbar.md](topbar.md) for a control in Roblox's top bar; [icons.md](icons.md) for any icon or image; [surface.md](surface.md) for fades, gloss and shine; [runtime.md](runtime.md) for live-data UI, performance and world-space GUIs.

## Workflow

Use this sequence for new UI or a substantial recreation; for small edits, revisit only decisions and checks the change affects. Detailed constraints below remain applicable.

1. **Set scope and inspect once.** Resolve the reference through [visual-style.md](../art/visual-style.md). Identify static Studio instances versus interactive/data-bound UI, supported orientations and delivery location. Read comparable theme tokens and image tables; inspect controller creation points only when needed for integration or to detect a second runtime HUD. Explain a coexistence issue early; do not change existing gameplay or bootstrap scripts merely to deliver a static design.
2. **Plan the complete artwork set.** Inventory every pictured icon and texture, including small topbar controls, repeated stats, offers and notifications. Check project images, then accessible [plugin libraries and Toolbox art](../safety/assets.md#plugin-asset-libraries). Compare the whole related group together on intended faces and enlarged on a neutral background using the [icon consistency check](icons.md). Decide keep/replace/missing for the set before assembly; matching button plates cannot reconcile incompatible artwork.
3. **Produce the missing set together.** Source or create the planned replacements in one production round, with shared style and outline specifications. This means planning all subjects upfront, not combining distinct assets into one generation call when the image tool requires separate calls. Review at full size and intended size before the [upload gate](../safety/uploading.md). Retain image results without printing their payloads. Reopen the asset plan only for an observed mismatch or a changed requirement, rather than accepting known mismatches and replacing them late.
4. **Validate a phone component, then assemble.** Start at the phone safe area with movement/jump zones reserved. Build one representative button/card and a compact icon/text/price row. Check the artwork, text, actual border bands, rounded corners and contained shine with a screenshot and UIBounds before duplicating the treatment across the HUD. Use shared construction helpers for one-time authoring, not copied ad hoc geometry. On TextButtons, set a plate's `UIStroke.ApplyStrokeMode = Border` explicitly; a contextual stroke does not outline an empty-text plate.
5. **Verify the assembled result.** Check phone (both orientations when supported), tablet and desktop using [the review requirements](#preview-and-measure-in-studio): bounds, independent component separation, touch sizes, longest supported values, image loading and visual consistency. Compare custom topbar controls with visible native controls in Play before claiming alignment. A clean bounds report alone does not prove these checks passed. After a local fix, recheck the affected views; do a final assembled pass without repeating unrelated discovery or production.
6. **Deliver and restore.** Remove temporary preview objects, builders, servers and intermediate files; restore settings and script enabled states to their recorded values. Keep required final artwork/asset ids unless the user requests their deletion. Report actual checks and unresolved limitations, including existing runtime HUD coexistence.

### Static StarterGui work ("don't code it")

Deliver editable native GUI instances and image artwork, without adding runtime Scripts, LocalScripts or ModuleScripts or wiring gameplay. One-time Studio authoring commands are acceptable unless the user forbids automation too. Keep labels, values and prices as native text; store asset ids in named attributes or value instances rather than adding a constants ModuleScript solely for the static design. Skip reactive state/controller work ([runtime.md](runtime.md)). Use isolated previews for verification; if existing scripts are temporarily disabled, record and restore their original states. Do not change game orientation or other gameplay settings to hide a layout failure. Disclose a required responsive behavior that cannot be delivered within the authorized static scope.

## Style

Match the selected layout, palette, typography, corners, outlines and image treatment. No fixed simulator/cartoon appearance is required. If that family is selected, load [styles/simulator-cartoon.md](../art/styles/simulator-cartoon.md) for its techniques. Other styles can be implemented directly from references. Keep captions, values and labels as editable native text, except lettering intrinsic to artwork.

## Mobile first

Roblox is a phone platform: **design, build and verify for the phone first**, then scale up to tablet and desktop, unless the user says otherwise. The smallest case is the case.

- Start from the phone's landscape size (about 844 x 390) and its safe area; add layout for larger screens with constraints, not the reverse. Reserve the thumbstick and jump/action zones; never put a control under them.
- Touch first: every button at least 44 px in both directions (after the device scale), no hover-only information, no tiny close buttons, text no smaller than about 11 px a line after scaling (`TextScaled` text wraps by itself when its box is tall enough, so `TextBounds.Y` can hold two lines).
- Verify at phone, then tablet, then desktop; with the Studio device emulator on, mouse input becomes touch. A script cannot send touch: [studio-testing.md](../code/studio-testing.md#play-tests-with-real-input). A layout that only works on desktop is unfinished.
- Unless the project says portrait is unsupported, check both orientations; if it is unsupported, say so and do not add portrait layouts.

## Stay in bounds

Nothing leaks out of its box unless the design says so. **A border stroke's band sits where its settings put it** ([UIStroke](https://create.roblox.com/docs/reference/engine/classes/UIStroke)):
- `BorderStrokePosition.Outer` (the default) draws it entirely outside the frame, so an element's outline adds its thickness on every side: a bar 1 px inside a rim still touches the rim once its own outline is counted. `Center` puts half outside, `Inner` none (the band then eats into the content area). `BorderOffset` moves it on (a scale of the frame's shorter side plus pixels).
- `StrokeSizingMode.ScaledSize` makes `Thickness` a share of the frame's shorter side (0.1 on a 200 x 300 frame is 20 px), so the outline grows with the device scale; `FixedSize` keeps pixels.
- An object may carry several border strokes (give each its own `ZIndex`); the widest sets the reach. On text objects only `ApplyStrokeMode.Border` outlines the box; the default `Contextual` outlines the glyphs.
- A `UIScale` scales the strokes, `BorderOffset` pixels and `UICorner` radii under it along with the elements.
- A double border entirely inside the frame: two `Inner` strokes, a dark one and a colored one moved inward by a negative scale `BorderOffset` (a `UIGradient` on the colored one for a rainbow).

- Children stay inside the parent with their outlines, keep **at least 2 px clear** of any border, rim or outline band, and stay clear of **rounded corners** (a child near a corner of a `UICorner` parent can poke out of the arc).
- Size content from the container's inner edge (rim inset plus stroke thickness), with a margin, not from its outer edge.
- Children of a `UIListLayout` or `UIGridLayout` box sit flush with its edge, so their outer outlines poke past it: draw those strokes `Inner`, or pad the box by the stroke.
- A visible fill inside a rounded track is never narrower than its two rounded ends, or its corners poke out of the track's. Convert the rendered corner diameter to a fraction of the track's width, clamp the fill's scale to that minimum, and keep its `Size` offsets at zero.
- A deliberate overlap (a badge breaking a card's corner, a glow, or a sunburst its parent clips) is marked with the boolean attribute `AllowBleed` and a comment that says why. Shine crossing a border needs the explicit design exception in [surface.md](surface.md). Do not silence findings with `AllowBleed`, remove a reference rim, or move a stroke merely to obtain a clean audit while leaving the visual defect.
- **Separate components stay separate.** Independent buttons, cards, panels and HUD groups must not intersect, clip, or cover each other's text, icons or outlines unless the user or design explicitly specifies that overlap. Measure their visible footprints, including outer strokes and decorations, and keep at least 4 px of visible clearance by default. This applies across different containers and ScreenGuis, not just siblings. A badge's intentional overlap with its own card does not permit that card to collide with another component; `AllowBleed` is not a waiver for unrelated collisions.
- Check with [scripts/UIBounds.luau](../../scripts/UIBounds.luau) on the mounted UI at the phone size first: `UIBounds.audit(frame)` reports `outside-parent`, `on-border`, `corner` and `outside-root` with pixel amounts. Fix the layout, not the audit.

## Layout rules

- **Scale-only size and position; topbar is the only offset exception.** Outside topbar UI components, every `Size` and `Position` uses `UDim2.fromScale(...)` or an equivalent `UDim2` with both offset fields set to `0`. Never use `UDim2.fromOffset(...)`, mixed scale-plus-offset dimensions, or pixel adjustments hidden in helpers or tween targets for body HUDs, menus, icons, inset faces, shine, counters or other non-topbar UI. Use scale-based grid cell sizes, layout spacing and padding too; convert measured pixel clearances to parent-relative scale. Constraints may enforce aspect ratios, minimum touch sizes and text limits without introducing offsets into `Size` or `Position`.
- **Preserve square controls:** when the reference shows a square plus/add button or icon, use a 1:1 `UIAspectRatioConstraint` on its visible plate. Independent width/height percentages are not a square guarantee. Check the rendered `AbsoluteSize` (width and height within 1px) and centre the plus glyph inside the border; a larger transparent touch target may surround the plate where space permits.
- **Reserve space for icon-and-amount rows:** give the icon a scale-sized, optionally aspect-constrained slot and place the amount in a separate slot using a horizontal layout. Left-align amounts and leave at least 4 rendered pixels between the icon and the text's outline, including at the smallest supported size and with the longest supported amount. A label passing `TextFits` or a bounds audit does not prove that it clears a sibling image. Check the friend-boost label and add button the same way.
- **Center anchor** *(default)*. Set `AnchorPoint = (0.5, 0.5)` and position by the element's center, so tweens of `Size`, `Rotation` and `Position` (pop-ins, scale-ups, shakes) grow from the middle. Use another anchor only when asked or when an edge must stay pinned (for example a bar that fills from the left).
- Use `UIAspectRatioConstraint`, `UISizeConstraint`, `UITextSizeConstraint` and `UIScale` for device scaling, and `UIListLayout`/`UIGridLayout`/`UIPadding` for layout, while preserving scale-only dimensions outside the topbar.
- `ScreenGui`: `ZIndexBehavior = Sibling`, and the safe area chosen per ScreenGui with `ScreenInsets`: `CoreUISafeInsets` keeps buttons and text clear of notches, rounded corners and Roblox's own top-bar buttons; `DeviceSafeInsets` clears only the device's cutouts; `TopbarSafeInsets` lays UI into the top bar beside Roblox's buttons; `None` is the whole screen (like `IgnoreGuiInset = true`) for full-bleed backgrounds and overlays. `ClipToDeviceSafeArea` and `SafeAreaCompatibility` decide what happens at the cut edges. Never put a control in a `None` ScreenGui on a phone. Where a project's windows already live in one, they stay (the project wins), and each window keeps clear of the top bar itself: it fits and centres in the screen below `GuiService:GetGuiInset()`. `ResetOnSpawn`: [runtime.md](runtime.md).

## Preview and measure in Studio

- **Check scale-only authoring before delivery:** inspect non-topbar instances and any code or tween targets that set their layout. Both offset fields of every `Size` and `Position` must be zero; check layout cell sizes, spacing and padding as well. A clean bounds audit does not establish this rule.
- **Visual review is required alongside the bounds audit.** At actual phone and desktop sizes, compare the complete icon group for consistent linework, shading and proportions; inspect faded stat backdrops over light and dark scenery for a smooth fade to transparency; and magnify every glossy edge/corner to confirm that shine and textures stay clear of the stroke except for documented design exceptions. Check moving shine at its extreme positions too. A zero-finding `UIBounds` report, `TextFits`, or successful image loading does not pass these visual checks. Fix failures and capture the affected details again before calling the UI complete.
- **Inspect compact HUD details at actual size:** capture the lower-corner stats and every price treatment, check square plates numerically, and measure icon/text and text/button clearance with strokes included. Exercise longest supported amounts and friend-boost percentages in a temporary preview, then restore the displayed values. Confirm native currency glyphs render in the selected font in Play; checking parent bounds alone misses these defects.
- **Mount a preview in CoreGui** (Edit): Studio shows it and never saves it with the place. `screen_capture` leaves CoreGui out, so move the preview into StarterGui only for a capture, then delete it, along with anything the code made on the way (sounds, groups).
- **Lay out against the device,** not the Studio window: a frame of the device's size holding the HUD at its own `UIScale`. `GuiService:GetGuiInset()` reads 0 in Edit, so a preview passes the top bar's height in.
- **Measure at each size,** once open tweens settle (Edit can run them late): UIBounds, the smallest text per line, every button's size, the distance to the top bar and the screen edges. Then the content extremes: the longest name and text, the lowest and highest values, optional parts hidden or shown.
- **Check topbar and component separation together:** phone landscape and portrait when supported, tablet, and desktop. For custom topbar controls, a **Play-mode comparison with the visible native controls is required before marking alignment verified**: confirm equal rendered plate height and vertical centre (within 1 rendered pixel, unless the reference explicitly specifies otherwise), fit inside the available rectangle, clearance from native controls, and separation from the first body card. Capture the native and custom controls together. Compare independent component rectangles in the same coordinate space, including those in separate ScreenGuis: an in-root UIBounds pass alone does not check every such collision. Edit mode can report zero insets; synthetic inset previews help layout but cannot pass this topbar check. If Play verification is unavailable, report the topbar alignment as unverified rather than calling the UI fully checked. Do not save preview-only inset overrides into the delivered UI.
- **Audit live screens at device sizes in Play:** a script cannot set the viewport, so move a live ScreenGui's children into a device-sized frame in a temporary ScreenGui, run UIBounds and capture, then move them back. `--@use` does not run on the client: load UIBounds as a temporary ModuleScript. This found three buttons under 44 px in a running match.
- **An unpublished place (PlaceId 0) may load none of the game's own images** (every one returned `AssetFetchStatus.Failure`). Judge art in the published place; images missing from such a preview are not a layout fault.
- **Keep Studio in the foreground for captures:** in the background it stops rendering 3D, so the world and every ViewportFrame come out blank while the GUI still draws. That is the environment, not a code fault.
- **Engine gotchas:** `TextFits` checks text against its own label only (a label wider than its parent still passes; UIBounds catches the leak). A `TextScaled` label with a `UITextSizeConstraint.MinTextSize` wraps long text and shows only the lines its box holds (two-word names showed their first word): make it tall enough for every line at that minimum, and check `TextFits` on every label at the phone size, since UIBounds reports nothing. `ScrollingFrame.CanvasSize` scale is measured against the frame's parent, not the frame (`fromScale(1, 1)` on a 1165 x 308 frame gave a 1240 x 880 canvas, the parent's), so scaled children sit too low and clip: compute the scale against the parent or use `AutomaticCanvasSize`; UIBounds skips scrolling content, so only a capture shows it; children of a `UIGridLayout` ignore `Rotation` (rotate a frame inside each cell); under a `UIScale`, `AbsoluteSize` is scaled, so lay out in logical points (`AbsoluteSize / scale`).
