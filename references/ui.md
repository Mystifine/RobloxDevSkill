# UI

Everything here applies to **ScreenGui, BillboardGui and SurfaceGui** alike; the world-space specifics are under World-space GUIs.

## Workflow

Use this sequence for new UI or a substantial recreation; for small edits, revisit only decisions and checks the change affects. Detailed constraints below remain applicable.

1. **Set scope and inspect once.** Resolve the reference through [visual-style.md](visual-style.md). Identify static Studio instances versus interactive/data-bound UI, supported orientations and delivery location. Read comparable theme tokens and image tables; inspect controller creation points only when needed for integration or to detect a second runtime HUD. Explain a coexistence issue early; do not change existing gameplay or bootstrap scripts merely to deliver a static design.
2. **Plan the complete artwork set.** Inventory every pictured icon and texture, including small topbar controls, repeated stats, offers and notifications. Check project images, then accessible [plugin libraries and Toolbox art](assets.md#plugin-asset-libraries). Compare the whole related group together on intended faces and enlarged on a neutral background using the [icon consistency check](#icons-and-images). Decide keep/replace/missing for the set before assembly; matching button plates cannot reconcile incompatible artwork.
3. **Produce the missing set together.** Source or create the planned replacements in one production round, with shared style and outline specifications. This means planning all subjects upfront, not combining distinct assets into one generation call when the image tool requires separate calls. Review at full size and intended size before the [upload gate](assets.md#uploading-open-cloud). Retain image results without printing their payloads. Reopen the asset plan only for an observed mismatch or a changed requirement, rather than accepting known mismatches and replacing them late.
4. **Validate a phone component, then assemble.** Start at the phone safe area with movement/jump zones reserved. Build one representative button/card and a compact icon/text/price row. Check the artwork, text, actual border bands, rounded corners and contained shine with a screenshot and UIBounds before duplicating the treatment across the HUD. Use shared construction helpers for one-time authoring, not copied ad hoc geometry. On TextButtons, set a plate's `UIStroke.ApplyStrokeMode = Border` explicitly; a contextual stroke does not outline an empty-text plate.
5. **Verify the assembled result.** Check phone (both orientations when supported), tablet and desktop using [the review requirements](#preview-and-measure-in-studio): bounds, independent component separation, touch sizes, longest supported values, image loading and visual consistency. Compare custom topbar controls with visible native controls in Play before claiming alignment. A clean bounds report alone does not prove these checks passed. After a local fix, recheck the affected views; do a final assembled pass without repeating unrelated discovery or production.
6. **Deliver and restore.** Remove temporary preview objects, builders, servers and intermediate files; restore settings and script enabled states to their recorded values. Keep required final artwork/asset ids unless the user requests their deletion. Report actual checks and unresolved limitations, including existing runtime HUD coexistence.

### Static StarterGui work ("don't code it")

Deliver editable native GUI instances and image artwork, without adding runtime Scripts, LocalScripts or ModuleScripts or wiring gameplay. One-time Studio authoring commands are acceptable unless the user forbids automation too. Keep labels, values and prices as native text; store asset ids in named attributes or value instances rather than adding a constants ModuleScript solely for the static design. Skip reactive state/controller work below. Use isolated previews for verification; if existing scripts are temporarily disabled, record and restore their original states. Do not change game orientation or other gameplay settings to hide a layout failure. Disclose a required responsive behavior that cannot be delivered within the authorized static scope.

## Style

Match the selected layout, palette, typography, corners, outlines and image treatment. No fixed simulator/cartoon appearance is required. If that family is selected, load [styles/simulator-cartoon.md](styles/simulator-cartoon.md) for its techniques. Other styles can be implemented directly from references. Keep captions, values and labels as editable native text, except lettering intrinsic to artwork.

### Faded backgrounds and shine

- **Identify color shading versus an opacity fade before building.** A shade behind a stat or text row that disappears into the game view needs a [UIGradient](https://create.roblox.com/docs/reference/engine/classes/UIGradient) with a varying `Transparency` `NumberSequence`. A uniformly translucent rectangle has a hard edge and does not reproduce that fade; changing `Color` alone does not fade to transparency.
- Put the gradient on a separate background Frame behind the icon and text, so the content stays fully visible. Set the Frame's base `BackgroundTransparency` low enough for the shade to show, then use gradient transparency keypoints to fade from the intended opacity to `1` at the disappearing edge. Match the fade's direction and extent with `Rotation`, `Offset` and keypoint positions. Keep `Color` constant for a pure opacity fade. In Studio-only work, author these instances and properties directly; no runtime script is needed.
- **Shine stays inside the face, clear of its strokes.** Frames are acceptable for shine bands, but size and inset their visible area from the innermost edge of every border/rim, including its thickness, offset, rounded corners and device scale. Keep the border continuous and unobscured. Match the reference's clearance; otherwise keep the normal 2 px interior margin. Rotating or animating a band must not carry its corners across the rim.
- Use a separate inset face for gloss and textures, with the outline drawn above it. Verify the actual rendered mask: a parent's `UICorner` or rectangular `ClipsDescendants` alone is not proof that a rotated child is contained by the rounded face. Use inset geometry or a suitable masked image when needed. A higher border `ZIndex` alone does not fix shine that extends outside the face.
- Only let shine cross a stroke when that overlap is explicitly present in the reference or requested design. Record that specific exception; do not infer it merely because the effect is decorative.

## Mobile first

Roblox is a phone platform: **design, build and verify for the phone first**, then scale up to tablet and desktop, unless the user says otherwise. The smallest case is the case.

- Start from the phone's landscape size (about 844 x 390) and its safe area; add layout for larger screens with constraints, not the reverse. Reserve the thumbstick and jump/action zones; never put a control under them.
- Touch first: every button at least 44 px in both directions (after the device scale), no hover-only information, no tiny close buttons, text no smaller than about 11 px a line after scaling (`TextScaled` text wraps by itself when its box is tall enough, so `TextBounds.Y` can hold two lines).
- Verify at phone, then tablet, then desktop; with the Studio device emulator on, mouse input becomes touch. A layout that only works on desktop is unfinished.
- Unless the project says portrait is unsupported, check both orientations; if it is unsupported, say so and do not add portrait layouts.

## Stay in bounds

Nothing leaks out of its box unless the design says so. **A border stroke's band sits where its settings put it** ([UIStroke](https://create.roblox.com/docs/reference/engine/classes/UIStroke)):
- `BorderStrokePosition.Outer` (the default) draws it entirely outside the frame, so an element's outline adds its thickness on every side: a bar 1 px inside a rim still touches the rim once its own outline is counted. `Center` puts half outside, `Inner` none (the band then eats into the content area). `BorderOffset` moves it on (a scale of the frame's shorter side plus pixels).
- `StrokeSizingMode.ScaledSize` makes `Thickness` a share of the frame's shorter side (0.1 on a 200 x 300 frame is 20 px), so the outline grows with the device scale; `FixedSize` keeps pixels.
- An object may carry several border strokes (give each its own `ZIndex`); the widest sets the reach. On text objects only `ApplyStrokeMode.Border` outlines the box; the default `Contextual` outlines the glyphs.
- A `UIScale` scales the strokes, `BorderOffset` pixels and `UICorner` radii under it along with the elements.

- Children stay inside the parent with their outlines, keep **at least 2 px clear** of any border, rim or outline band, and stay clear of **rounded corners** (a child near a corner of a `UICorner` parent can poke out of the arc).
- Size content from the container's inner edge (rim inset plus stroke thickness), with a margin, not from its outer edge.
- Children of a `UIListLayout` or `UIGridLayout` box sit flush with its edge, so their outer outlines poke past it: draw those strokes `Inner`, or pad the box by the stroke.
- A visible fill inside a rounded track is never narrower than its two rounded ends, or its corners poke out of the track's. Convert the rendered corner diameter to a fraction of the track's width, clamp the fill's scale to that minimum, and keep its `Size` offsets at zero.
- A deliberate overlap (a badge breaking a card's corner, a glow, or a sunburst its parent clips) is marked with the boolean attribute `AllowBleed` and a comment that says why. Shine crossing a border needs the explicit design exception described above. Do not silence findings with `AllowBleed`, remove a reference rim, or move a stroke merely to obtain a clean audit while leaving the visual defect.
- **Separate components stay separate.** Independent buttons, cards, panels and HUD groups must not intersect, clip, or cover each other's text, icons or outlines unless the user or design explicitly specifies that overlap. Measure their visible footprints, including outer strokes and decorations, and keep at least 4 px of visible clearance by default. This applies across different containers and ScreenGuis, not just siblings. A badge's intentional overlap with its own card does not permit that card to collide with another component; `AllowBleed` is not a waiver for unrelated collisions.
- Check with [scripts/UIBounds.luau](../scripts/UIBounds.luau) on the mounted UI at the phone size first: `UIBounds.audit(frame)` reports `outside-parent`, `on-border`, `corner` and `outside-root` with pixel amounts. Fix the layout, not the audit.

## Layout rules

- **Scale-only size and position; topbar is the only offset exception.** Outside topbar UI components, every `Size` and `Position` uses `UDim2.fromScale(...)` or an equivalent `UDim2` with both offset fields set to `0`. Never use `UDim2.fromOffset(...)`, mixed scale-plus-offset dimensions, or pixel adjustments hidden in helpers or tween targets for body HUDs, menus, icons, inset faces, shine, counters or other non-topbar UI. Use scale-based grid cell sizes, layout spacing and padding too; convert measured pixel clearances to parent-relative scale. Constraints may enforce aspect ratios, minimum touch sizes and text limits without introducing offsets into `Size` or `Position`.
- **Preserve square controls:** when the reference shows a square plus/add button or icon, use a 1:1 `UIAspectRatioConstraint` on its visible plate. Independent width/height percentages are not a square guarantee. Check the rendered `AbsoluteSize` (width and height within 1px) and centre the plus glyph inside the border; a larger transparent touch target may surround the plate where space permits.
- **Reserve space for icon-and-amount rows:** give the icon a scale-sized, optionally aspect-constrained slot and place the amount in a separate slot using a horizontal layout. Left-align amounts and leave at least 4 rendered pixels between the icon and the text's outline, including at the smallest supported size and with the longest supported amount. A label passing `TextFits` or a bounds audit does not prove that it clears a sibling image. Check the friend-boost label and add button the same way.
- **Center anchor** *(default)*. Set `AnchorPoint = (0.5, 0.5)` and position by the element's center, so tweens of `Size`, `Rotation` and `Position` (pop-ins, scale-ups, shakes) grow from the middle. Use another anchor only when asked or when an edge must stay pinned (for example a bar that fills from the left).
- Use `UIAspectRatioConstraint`, `UISizeConstraint`, `UITextSizeConstraint` and `UIScale` for device scaling, and `UIListLayout`/`UIGridLayout`/`UIPadding` for layout, while preserving scale-only dimensions outside the topbar.
- `ScreenGui`: `ZIndexBehavior = Sibling`, and the safe area chosen per ScreenGui with `ScreenInsets`: `CoreUISafeInsets` keeps buttons and text clear of notches, rounded corners and Roblox's own top-bar buttons; `DeviceSafeInsets` clears only the device's cutouts; `TopbarSafeInsets` lays UI into the top bar beside Roblox's buttons; `None` is the whole screen (like `IgnoreGuiInset = true`) for full-bleed backgrounds and overlays. `ClipToDeviceSafeArea` and `SafeAreaCompatibility` decide what happens at the cut edges. Never put a control in a `None` ScreenGui on a phone. Where a project's windows already live in one, they stay (the project wins), and each window keeps clear of the top bar itself: it fits and centres in the screen below `GuiService:GetGuiInset()`. `ResetOnSpawn` is covered under State.

## Topbar controls

- Topbar UI components may use offset sizing and positioning to match the measured native Roblox controls. This exception applies to the topbar and its contents, not to a body card merely placed near the top of the screen.
- **Identify the native Roblox topbar first:** in a running client, it is the Roblox-logo button and the adjacent dark menu/chat/microphone controls at the top left. Custom quick-access buttons extend that same visual row; the Studio toolbar, the screen's top edge, and an empty Edit preview are not alignment references.
- A button or frame intended for the topbar belongs **inside the available topbar rectangle**, not at a percentage of the full-screen HUD height. Prefer a separate `ScreenGui` with `ScreenInsets = TopbarSafeInsets`, `ResetOnSpawn = false` and `SafeAreaCompatibility = None`. Its origin and available size follow the engine's dynamic [topbar safe area](https://create.roblox.com/docs/reference/engine/enums/ScreenInsets), including notches and Roblox's experience controls.
- **Match native CoreGui control height unless explicitly specified otherwise.** A custom topbar button or frame must have the same rendered height as Roblox's adjacent native controls at the current device/UI scale, including outer strokes; match their vertical centre too. Measure the native control's visible plate, not its glyph or the full `TopbarInset.Height`. Merely fitting the inset, or copying an oversized project button, is insufficient. Use the inset for placement and CoreGui control height for sizing; preserve aspect ratio and scale the inner icon proportionally. Never size from viewport height or a body-HUD scale. A separate transparent touch target may meet the 44 px minimum where space permits, without enlarging the visible plate or overlapping nearby controls.
- `TopbarSafeInsets` already applies the topbar position offset: do not apply it twice. If an existing custom layout must position the control in another coordinate space, convert the full `GuiService.TopbarInset` rectangle into that space, including its `Min` offset, and update when `TopbarInset` changes. A fixed desktop topbar height or negative Y offset is not a device-independent solution.
- `TopbarSafeInsets` supplies a rectangle; it does **not** align its children with the native plates. Measure the native plate's top, bottom and centre in Play and choose anchors/layout within that rectangle accordingly. Neither pinning a child to `Y = 0` nor centring it in the whole inset proves alignment. Compare coordinates in the same space; `AbsolutePosition` can include a GUI-inset offset, so confirm the result in the rendered client too.
- Place body cards and status panels below the topbar in a `CoreUISafeInsets` container, or explicitly reserve the topbar rectangle in their existing layout. Leave the required visible gap between the topbar control's outermost edge and the first body component. Changing ZIndex, hiding overflow with clipping, or marking an accidental collision `AllowBleed` does not fix the layout.

## Preview and measure in Studio

- **Check scale-only authoring before delivery:** inspect non-topbar instances and any code or tween targets that set their layout. Both offset fields of every `Size` and `Position` must be zero; check layout cell sizes, spacing and padding as well. A clean bounds audit does not establish this rule.
- **Visual review is required alongside the bounds audit.** At actual phone and desktop sizes, compare the complete icon group for consistent linework, shading and proportions; inspect faded stat backdrops over light and dark scenery for a smooth fade to transparency; and magnify every glossy edge/corner to confirm that shine and textures stay clear of the stroke except for documented design exceptions. Check moving shine at its extreme positions too. A zero-finding `UIBounds` report, `TextFits`, or successful image loading does not pass these visual checks. Fix failures and capture the affected details again before calling the UI complete.
- **Inspect compact HUD details at actual size:** capture the lower-corner stats and every price treatment, check square plates numerically, and measure icon/text and text/button clearance with strokes included. Exercise longest supported amounts and friend-boost percentages in a temporary preview, then restore the displayed values. Confirm native currency glyphs render in the selected font in Play; checking parent bounds alone misses these defects.
- **Mount a preview in CoreGui** (Edit): Studio shows it and never saves it with the place. `screen_capture` leaves CoreGui out, so move the preview into StarterGui only for a capture, then delete it, along with anything the code made on the way (sounds, groups).
- **Lay out against the device,** not the Studio window: a frame of the device's size holding the HUD at its own `UIScale`. `GuiService:GetGuiInset()` reads 0 in Edit, so a preview passes the top bar's height in.
- **Measure at each size,** once open tweens settle (Edit can run them late): UIBounds, the smallest text per line, every button's size, the distance to the top bar and the screen edges. Then the content extremes: the longest name and text, the lowest and highest values, optional parts hidden or shown.
- **Check topbar and component separation together:** phone landscape and portrait when supported, tablet, and desktop. For custom topbar controls, a **Play-mode comparison with the visible native controls is required before marking alignment verified**: confirm equal rendered plate height and vertical centre (within 1 rendered pixel, unless the reference explicitly specifies otherwise), fit inside the available rectangle, clearance from native controls, and separation from the first body card. Capture the native and custom controls together. Compare independent component rectangles in the same coordinate space, including those in separate ScreenGuis: an in-root UIBounds pass alone does not check every such collision. Edit mode can report zero insets; synthetic inset previews help layout but cannot pass this topbar check. If Play verification is unavailable, report the topbar alignment as unverified rather than calling the UI fully checked. Do not save preview-only inset overrides into the delivered UI.
- **An unpublished place (PlaceId 0) may load none of the game's own images** (every one returned `AssetFetchStatus.Failure`). Judge art in the published place; images missing from such a preview are not a layout fault.
- **Keep Studio in the foreground for captures:** in the background it stops rendering 3D, so the world and every ViewportFrame come out blank while the GUI still draws. That is the environment, not a code fault.
- **Engine gotchas:** `TextFits` checks text against its own label only (a label wider than its parent still passes; UIBounds catches the leak); children of a `UIGridLayout` ignore `Rotation` (rotate a frame inside each cell); under a `UIScale`, `AbsoluteSize` is scaled, so lay out in logical points (`AbsoluteSize / scale`).

## State

- **`ResetOnSpawn = false` on nearly every GUI container** (ScreenGui, and any BillboardGui or SurfaceGui parented under PlayerGui: HUD, menus, shop, tutorial, offers). Build once at join and keep it across respawns; with the default `true` the whole UI is destroyed and rebuilt on every death, losing open windows, scroll positions, tweens and connections. Only UI that truly belongs to one character (an overhead billboard) lives and dies with it.
- **State lives outside the instances.** Keep one source of truth per fact (a store, a Pulse/signal value or the replicated save), and have the UI render from it and write back through it: never read a TextLabel's text or a Frame's `Visible` to decide logic. Views subscribe, update only when the value changes, and are safe to show, hide and re-show. State means facts (data, the open window, a selection), not every property: a reactive value or effect per instance property costs far more than the write it wraps.
- **Survive respawn, rejoin and teleport:** derive what is open or selected from the store, re-bind to the new character (`CharacterAdded`) instead of rebuilding the UI, and restore on join from the saved or replicated state. Disconnect every listener when a view closes or is destroyed, and keep temporary state (a hover, a draft) out of the save.

## World-space GUIs (BillboardGui, SurfaceGui)
- **BillboardGui defaults: scaled size, world-space placement.** Size with Scale (`UDim2.fromScale`, so it is measured in studs and shrinks with distance like the world), with both `Size` offsets at zero. Position it with `StudsOffsetWorldSpace` (a world-space lift above the adornee, which stays above the head however the camera turns); this world-space property is distinct from a UI dimension's pixel offset. Set `Adornee`, `MaxDistance` and `AlwaysOnTop` deliberately (always-on-top only for pointers that must show through walls), `LightInfluence = 0` for UI, and keep it small and cheap: one per target, not per frame.
- **SurfaceGui:** fix its `Face`, set `SizingMode` and `PixelsPerStud` deliberately (a legible density at the distance it is read), `LightInfluence` and `AlwaysOnTop` on purpose, and keep text large enough to read at that distance.
- The same rules still apply inside them: bounds and rounded corners, readable text, the project's theme, build once and show or hide, state outside the instances.

## Performance

- Build once, then show/hide; do not recreate frames on every open. Pool list rows and virtualize long lists.
- Update text/images only when the value changes. No per-frame property writes for static UI; drive animation with `TweenService` or one shared loop.
- Avoid stacked full-screen transparent frames, many `UIStroke`/`UIGradient` on large lists, and deep `ClipsDescendants` chains.

## Icons and images

- **Recognize Roblox's native Robux symbol:** the angular coin with a square hole is available as the Roblox-specific character U+E002: `utf8.char(0xE002)` or `"\u{E002}"`. Prefer that glyph for Robux prices instead of drawing a token, using a generic circle/hexagon, or generating/uploading an imitation. Put the glyph, a space, and the amount in one native TextLabel when they share styling (`"\u{E002} 95"`); use `TextColor3` and a contextual `UIStroke` to match the reference. This private-use character is not a universally supported Unicode currency sign: verify its actual rendering in the chosen font/client, including the square hole and baseline. See the [Roblox glyph reference](https://devforum.roblox.com/t/unicode-characters-for-roblox-plus-premium-verified-and-robux/2175425).
- **Match the selected image family:** preserve its silhouettes, palette, shading, linework and border treatment through [visual-style.md](visual-style.md). Do not add gloss, cartoon outlines or a sticker border unless the direction calls for them. UI labels stay native text, except artwork intrinsic to an icon, such as a calendar's number.
- **Pictorial icons stay image artwork when their family is illustrated.** Use matching images for every subject in that family, including small topbar checklist/clipboard, calendar and settings icons. A simple subject is not permission to substitute stacked Frames, a Unicode/emoji glyph or a flat code-drawn icon beside painted/shaded artwork. Reuse a compatible image or create one through the same fallback workflow as larger icons. Native geometry remains appropriate for layout, plates, borders, shine, simple plus/close marks and an explicitly geometric/vector icon family; the native Robux glyph above is also an exception. If matching pictorial art cannot be obtained, mark and report a temporary placeholder instead of presenting the geometric substitute as finished.
- **Reuse is conditional on icon consistency:** compare candidate icons side by side with the selected family, on the intended button faces at their rendered size and enlarged on a neutral background. Check outline color/weight and sticker borders, flat versus shaded/3D treatment, lighting and gloss, palette, perspective, proportions, detail density, and transparent edge quality. Apply this to project, plugin and Toolbox art alike, including icons inside reused buttons. The same subject, colors, or broad label such as "cartoon" is insufficient; a flat emoji beside painted glossy icons fails this check unless that mix is explicit in the design. Repeated uses of one stat/currency must use the same artwork and treatment. Different functional groups may use different families only when supported by the reference or chosen design.
- **Fallback when reuse fails:** search for a complete compatible set before mixing individual finds. If matching art is unavailable, create or edit coherent replacements in the selected style when possible. If that is unavailable or outside the authorized scope, use a consistent temporary placeholder treatment for the missing icons, mark them `Placeholder = true`, and report what is missing and how to replace it. Do not silently fill gaps with stylistically incompatible art or present placeholders as a finished match. Search matching project images, then compatible plugin libraries and Toolbox art ([assets.md](assets.md)); source availability never changes the selected style.
- Generate icons as **512x512, 1:1 (square), transparent-background PNG** *(default)* (smaller memory on clients); downscale a generator's larger square output with premultiplied-alpha LANCZOS. If a generator cannot output transparency, remove the background and confirm the alpha channel before upload. Use a different size or aspect only for non-icon art (banners, hero art), with the user's agreement.
- **Outlines match the set.** Before generating, measure the siblings' edge with [scripts/icon_outlines.py](../scripts/icon_outlines.py): a viewer shows transparency as white, which hides a white sticker border. Give every new or edited icon the same edge (a dark ink line, a white sticker border of the same width, or none). An edit never adds or drops a border, and a brief states the measured style, never one remembered.
- **Character art** follows [characters.md](characters.md): put its garment line in the prompt and review at full size before upload.
- **Damage, health and defeat icons** are uploads and follow [no-gore.md](no-gore.md): a burst or star for damage, a heart for health, a cartoon skull or KO stars for defeats; never blood drops, splatter or wounds.
- **Uploads** use the project's cloud API key and must load in the experience: [assets.md](assets.md), Uploading.
- For interactive UI, all image ids live in the project's image-asset table (or one new constants module), never inline in controllers, so a replacement is a one-line change. Static instance delivery uses the named asset values/attributes described above.
- For interactive UI, preload important images (`ContentProvider:PreloadAsync`) before showing a screen that depends on them. Verify loads through the actual ImageLabel/ImageButton or its `IsLoaded` state: a raw id-string preload can report Failure even for a displayed asset. Static delivery needs a loading check in preview/Play, not a new preload script.
