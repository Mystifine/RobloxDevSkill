# Onboarding, tutorials and funnels

## Tutorial design: show, don't tell
- **One short sentence per step** (aim 3-6 words: "Tap the gate"). Motion, glow and pointers teach; text only names the action. No paragraphs, no stacked tips.
- **One step = one target + one player action.** It completes on the action itself (tap, move, pickup), never a Next button. Reward each step at once (sound, pop, currency); get the player acting within about 20 s of joining.
- **Assist heavily.** The player always sees where to look, go or press. Re-point after about 6 s idle and after a failed try; a stuck player never guesses.
- **Enforced and dummy-proof** *(default)*. The player cannot reset, open other UI, trigger other features or do anything that breaks the lesson: disable the reset button (`SetCore("ResetButtonCallback", false)`), hide every HUD piece and window the step does not use, disable what it does not need (shop, offers, teleports, other keybinds, popups, monetization prompts), block input outside the target, and make the player unable to die or fall out of the area. Reveal UI as it is taught. Relax this only for tutorials that are explicitly suggestive, optional or non-enforcing (a tip, a hint ring); say so in the design.
- **Server owns progress.** Validate each step on the server and reject out-of-order or unexpected requests; steps are idempotent, never farmable or blockable. Persist only completion. **Leaving mid-tutorial resets the whole run** *(default)*: the next join starts at step 1 and anything the tutorial granted or spawned is undone. Cutscenes keep their required skip, which restores state through its own path.
- **Mobile first.** Targets at least 44 px, pointers inside safe insets, check with the device emulator on touch.

## Pointers: pick one per target, never stack them
| Target | Use |
|---|---|
| UI element | Focus cut-out: a rounded frame with a huge UIStroke running off screen darkens everything else; ring ping; bobbing arrow |
| Nearby 3D object | Same dark focus around the object's projected bounds (or Highlight), plus a floating billboard arrow above it (AlwaysOnTop, bob about 1 Hz, a few px) |
| Far place | Beam from the character to the target, both ends about 1.5 studs above the floor (ground the target with a ray, then lift) so it never digs in; fade both ends; flowing chevrons |
| Key reveal | Camera nudge of 2 s or less, then hand control back. Never during movement lessons |

Templates: [scripts/TutorialGuide.luau](../scripts/TutorialGuide.luau): `spotlight` (dark hole plus input sinks), `screenRect`, `arrow`, `beam`, `lookAt`, `lock` (hide HUD, sink keys, restore). Checked in Studio. Use the project's own pointer or beam first if it has one, and match its style.

## Funnels (AnalyticsService; Creator Hub limits table checked 2026-10-27)
**Limits:** up to 10 funnels (the docs do not say whether onboarding counts: plan at most 9 including it and build only what is needed now), 100 steps each, server only, published places only. Only a step's first instance counts (repeats still spend rate budget); skipping ahead completes earlier steps; a saved step expires after 180 days. One-time funnels need no `funnelSessionId`; recurring ones do (a GUID or `<playerId>-<itemId>`; the last 10 per user are tracked). Up to 3 custom fields (`Enum.AnalyticsCustomFieldKeys.CustomField01..03.Name`, string values): unlimited values per field, but past 8,000 combined values they are grouped as "Other". One rate budget for all events: 120 + 20 per CCU per minute.

**Rules**
- Design the set once and reuse it forever: no V2/V3, no renames (a step-name change only shows a warning on the step); keep meanings stable and append steps, never reorder.
- **A custom field is a segment label, fixed when the player enters the funnel.** Every step of one funnel session sends the same values; a value that changes mid-funnel splits one player across segments. Anything that changes (time since start, blockers, resources) is a custom **event** or event value, not a field.
- **Scheme** *(default)*. Lifetime funnels: field 1 `Origin - <Cohort>_T<tutorial>_A<schema>_B<build at enrollment>`, fields 2-3 constant. Per-attempt funnels (a run, a gate): the same Origin without the build, field 2 a bounded context (dungeon or tier), field 3 a bounded state (readiness, party), both **frozen at session start**. Onboarding: Cohort / `Version - N; Build - N` / Content. Bump the tutorial or schema number only when its meaning changes.
- **Keep every field's value set bounded** for the funnel's whole life: bucket long tails (24 dungeons into about 6 tiers), one spelling per meaning (a new spelling starts a new series), no raw numbers, GUIDs or names. Write values as `Dimension - Value`. The three fields multiply, so a value that changes every publish belongs only where the other two fields have few values.
- **Sync the published build automatically**: `game.PlaceVersion` is the number in the place's Version History (0 if never published). Read it server-side, label Studio separately, and remember a server keeps the version it started on. A funnel spanning days or publishes freezes the build with its enrollment (saved beside the cohort), or one player's steps land in different builds. Where a field cannot afford a value per publish, compare builds by date range instead. Never a new funnel for a build.
- **Onboarding funnel**: one step per lesson in order, named by the action, logged on server validation (never on UI show).
- **Progression funnels are post-tutorial** *(default)*, so they show how players who finished the tutorial behave. The server enrolls a player when it saves the tutorial as complete and sends no progression step, lifetime or per attempt, before that: the onboarding funnel covers the tutorial, and a milestone the tutorial scripts or grants (a guided first run, a starter pet) says nothing about what players choose. Step 1 of every lifetime progression funnel is that enrollment (`Post tutorial`), so they all start from the same count of graduates. Players who finished the tutorial before the funnels shipped enroll on their next join as their own cohort (`Existing`); read the new graduates (`Fresh`). Persist cohort, labels and step cursors in the save so a returning player keeps them. A game without a tutorial enrolls on first join.
- **One funnel per progression feature** *(default)*: the core loop, each system (pets, base, crafting) and the tier ladder get a funnel of their own, holding only that feature's first-time milestones in its own order (a few to 20 within about the first 2 hours: first run, first clear, first return; first upgrade, second, third). Features advance in parallel and logging a later step completes every earlier one, so a mixed funnel records steps the player never took and hides which feature loses them. Within a funnel, send a step only after its predecessors (hold one that arrives early); an optional step (a chest, a side shop) gets its own funnel or a custom event. The funnel limit covers the main features only; measure the rest with custom events.
- Failures and friction (cannot afford, storage full) are custom events with a bounded reason list, not steps.
- Test the step order with a mock transport; real data appears only from published servers.

Docs: [funnel events](https://create.roblox.com/docs/production/analytics/funnel-events), [custom fields](https://create.roblox.com/docs/production/analytics/custom-fields), [limits](https://create.roblox.com/docs/production/analytics/event-types).
